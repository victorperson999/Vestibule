02 / Architecture

Inside the Isolation Chamber

Native Linux isolation below (no Docker, no root). On Windows, macOS, and stock Ubuntu 23.10+, Vestibule runs a locked-down throwaway container via src/vestibule/backends/container.py.

Clean MCP Server

The long-lived stdio MCP server decides whether and what may run, and never executes untrusted code in its own process.

  • Validates language (python, node, bash), caps code size (256 KiB), and clamps timeout_seconds to VESTIBULE_MAX_TIMEOUT_S (default 60 s) before spawning anything.
  • Returns errors as readable Blocked: … content so the agent adapts without crashing the MCP session.
  • Writes paired start / end JSONL records to ~/.vestibule/audit/ (code up to 4 KiB, usage, isolation verdict, output byte sizes — never output contents).

Source: src/vestibule/server.py, src/vestibule/audit.py

Unprivileged Warden Helper

Each native run spawns a fresh helper process that prepares isolation from outside the sandbox, with zero root privileges.

  • Placed from outside into a per-run systemd user cgroup v2 scope enforcing memory.max, memory.swap.max=0, cpu.max, and pids.max.
  • Compiles the Docker-derived libseccomp allowlist (refusing dangerous syscalls and AF_VSOCK) before pivot_root.
  • Calls unshare(CLONE_NEWUSER | CLONE_NEWPID), writes an identity uid/gid map (your own user ID, never root), and forks PID 1 init.
  • Stays outside the PID namespace so the guest cannot see or signal it: answers seccomp user-notify with EPERM, kills init via pidfd on timeout, and reads final cgroup usage counters after init exits.

Source: src/vestibule/backends/native_helper.py, src/vestibule/backends/native_cgroup.py, src/vestibule/backends/native_seccomp.py

Sandbox PID 1 Init

Inside the new PID namespace, the forked init process becomes PID 1, seals the remaining kernel boundaries, and supervises the guest.

  • Calls setsid() and unshares CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWCGROUP (network namespace with lo only).
  • Mounts and enters a pivot_root jail over the read-only unpacked rootfs plus /workspace, a size-capped /tmp, and read-only /sandbox.
  • Drops all capabilities, sets PR_SET_DUMPABLE=0 and PR_SET_NO_NEW_PRIVS=1, loads the compiled libseccomp filter, and runs kernel self-checks.
  • Forks the guest process and reaps orphan children; when the helper kills PID 1, the kernel terminates the entire PID namespace.

Source: src/vestibule/backends/native_helper.py

Guest Process & /workspace Doorway

The untrusted Python 3.12, Node 22, or Bash snippet sees only the pinned rootfs, a capped /tmp, and /workspace.

  • Host files outside /workspace do not exist inside the mount namespace; outbound TCP, UDP, DNS, and AF_VSOCK fail immediately.
  • read_workspace reads files from the host side through a handle/descriptor-relative path jail that refuses symlinks and traversal.
  • vestibule-mcp ui provides an opt-in, strictly read-only local web inspector over your audit log and workspace using the exact same jail.

Source: src/vestibule/workspace.py, src/vestibule/ui_cli.py

04 / Security

Honest Threat Model

Summary of SECURITY.md §1. Every run ends with an honest isolation: verdict stating what actually applied.

What holds

For a run reporting isolation: native or isolation: container, short of a bug in the kernel or the container runtime:

  • Host files outside /workspace are unreachable from the sandbox.
  • No network egress — empty network namespace (lo only) and AF_VSOCK blocked by seccomp on native.
  • Resource caps enforced — memory (no swap), CPU, process count (pids.max), /tmp size, and wall-clock timeout.
  • Honest isolation reporting on every run (native, container, native-degraded, container-degraded, none, or Blocked:).

What stays possible & what it isn't

Clear boundaries before trusting any sandbox with real credentials or projects:

  • Not a VM. On Linux, the sandbox shares your host kernel, so a kernel bug that escapes a namespace would escape Vestibule. (On Windows/macOS, Docker Desktop's Linux VM is Docker's boundary, not Vestibule's.)
  • Only run_code is sandboxed. Your agent's own shell and file tools still run on your machine unless you restrict them.
  • /workspace is writable and uncapped on disk (unless VESTIBULE_WORKSPACE_RO=1) and may contain guest-planted symlinks. read_workspace and vestibule-mcp ui refuse symlinks — don't point VESTIBULE_WORKSPACE at an existing project folder.
  • Run output returns to your agent and is sent to its model provider.
  • Untested environments: arm64 Linux hosts, Podman, and sandboxed container runs on macOS.

Full threat model, test citations, and known residuals: SECURITY.md · Report a vulnerability privately via GitHub Security Advisories.
